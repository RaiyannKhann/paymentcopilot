# Decisions Log

Dated tradeoff decisions for Payment Copilot.

## 2026-08-13 — Phase 1 tech choices

- **Embeddings:** local `sentence-transformers/all-MiniLM-L6-v2` instead of OpenAI embeddings, to keep cost near zero during dev and avoid an extra API dependency.
- **LLM default:** `claude-haiku-4-5` for cost-effective iteration, swappable to `claude-sonnet-5` via `ANTHROPIC_MODEL` env var for higher-quality demo runs.
- **Dependency management:** plain `venv` + `requirements.txt` (via `pyproject.toml` dynamic dependencies for editable install) rather than Poetry — Poetry was broken in the dev environment (bad interpreter) and not worth repairing for a small Phase 1 dependency set.
- **Docs corpus:** 15 original, hand-authored markdown docs modeled after Razorpay/Stripe-style documentation, not scraped from any real provider — avoids ToS risk and keeps content clearly labeled as synthetic/original.
- **Multi-tenancy:** single Pinecone index with a `tenant_id` metadata field added to every vector from Phase 1 onward (even though unused until Phase 2's routing/filtering), to avoid a future re-ingestion migration.
- **Scope:** no FastAPI, LangGraph/LangChain, guardrails, Redis, or Docker in Phase 1 — CLI-only, with retrieval/generation written as plain typed functions so Phase 2's LangGraph router can wrap them as nodes without a rewrite.

## 2026-08-13 — Phase 2 tech choices

- **Postgres setup:** used the local Postgres 14 service already running on this machine (via Homebrew, pre-existing from another project) rather than installing a second version or introducing Docker early — created an isolated `paymentcopilot` database, left the other project's `eduai_db` untouched. Docker remains deferred to Phase 5 as originally planned.
- **Routing method:** deterministic regex/keyword heuristics (`graph/classify.py`), not a dedicated LLM classifier call — matches FR2's wording most literally ("deterministic and inspectable... not a black-box single LLM call"), and avoids adding latency/cost to every query just for routing.
- **Tenant scoping fix:** Phase 1 filtered ALL Pinecone retrieval by `tenant_id`, which only worked because there was a single implicit tenant. Corrected in Phase 2: docs/policy content is platform-wide (shared across all merchants), so retrieval now filters by `doc_type` ("docs" vs "policy") instead. `tenant_id` metadata is retained on vectors but no longer filtered by default. The real multi-tenant boundary (FR19) is the transactions table — `structured/lookup.py` scopes every query by `(txn_id, merchant_id)`, confirmed to return "not found" rather than leaking data across merchants.
- **Pinecone re-ingestion:** chunk IDs are now hashed from `(doc_type, source_doc, chunk_index)` instead of `(source_doc, chunk_index)`, since docs and policy corpora could otherwise collide. This changed all vector IDs, so the index was reset (`ingest --reset`) rather than left with orphaned Phase-1-era vectors.
- **UC3 confidence threshold:** set to `0.45` (cosine similarity, top-1 chunk) as a provisional default — PRD §14 explicitly flags this as something to tune empirically against the golden eval set in Phase 4, not fix arbitrarily. Configurable via `UC3_CONFIDENCE_THRESHOLD` env var.
- **UC3 escalation wording:** the model is instructed to emit a fixed sentinel token (`NEEDS_ESCALATION`) rather than freely phrasing its own refusal, which the code then maps to the exact PRD §6.3 escalation message. This guarantees the non-evasive, compliance-safe wording regardless of model phrasing drift.
- **Synthetic transactions:** 40 transactions across 3 merchants (`demo-merchant`, `acme-retail`, `globex-travel`), generated deterministically (fixed seed 42) by `scripts/generate_transactions.py` into a version-controlled CSV, then loaded via `scripts/seed_transactions.py` — per PRD §5.3, generation is scripted and reproducible, not hand-edited.

## 2026-08-14 — Phase 3 tech choices

- **Guardrails as LangGraph nodes, not ad-hoc checks in `run_query()`:** FR2 requires routing to stay "deterministic and inspectable (LangGraph node path visible in logs)" — a plain Python check wrapped around `_graph.invoke()` would be invisible to that same inspection mechanism. `input_guardrail`/`blocked`/`output_guardrail` are first-class nodes, same category as `classify`/`uc1_docs`/etc.
- **Regex/heuristic injection detection, not NeMo Guardrails or a classifier:** resolves PRD §14's open question in favor of hand-rolled, matching §6.1's "heuristic/regex initially, upgradeable to classifier." Zero new runtime dependency; five pattern categories (instruction override, role-play/jailbreak, system-prompt exfiltration, payments-domain cross-tenant exfiltration, delimiter/escape) in `guardrails/injection.py`. Known tradeoff, documented in `tests/test_injection.py`: regex can't distinguish "ignore" used innocuously from an override attempt without more context — acceptable for Phase 3, revisit if false positives show up in real usage.
- **Presidio for PII (FR11), `en_core_web_sm` not `en_core_web_lg`:** entity list (`CREDIT_CARD`, `EMAIL_ADDRESS`, `PHONE_NUMBER`, `IBAN_CODE`, `US_SSN`, `US_BANK_NUMBER`) is deliberately pattern-based-recognizer-only — excludes `PERSON`/`LOCATION`, which need NLP-model quality and risk false-positive redaction of merchant/product names in this domain. Since the chosen entities don't depend on NLP quality, the small spaCy model is enough; no reason to pay `en_core_web_lg`'s footprint.
- **Redact, don't block, for PII in both directions:** input PII (FR11) and output PII leaks (FR14) are redacted in place rather than causing a refusal/suppression — matches §6.1/§6.2's literal action wording ("redact before forwarding/logging" / "redact or suppress") and preserves an otherwise-useful answer instead of discarding it over one incidental PII span.
- **LLM-as-judge for faithfulness (FR13), not RAGAS:** full RAGAS + the 30-50 item golden dataset is explicitly Phase 4 scope (§11); §6.2 permits "RAGAS metric **or** LLM-as-judge at inference time," so Phase 3 implements the latter — one extra Claude call per non-escalated answer (`guardrails/faithfulness.py`), reusing the existing retry-wrapped `generator.call_claude` (renamed from `_call_claude` to make it a proper shared symbol across modules).
- **UC2 structured-field injection → deterministic trusted-fields fallback, not sanitize-and-continue or full refusal:** a flagged `description` causes `_uc2_node` to skip the Claude call entirely and answer from verified DB columns only. Silent sanitize-and-continue would still let attacker-influenced text shape prompt construction; a full refusal would make every transaction with a flagged description unexplainable over a field that's cosmetic to the actual facts. Caught and fixed a real bug during this work: the output-guardrail's UC2 grounding text initially didn't match what the model's own prompt showed it (missing `txn_id`/`merchant_id`/the "smallest currency unit" note), causing the faithfulness judge to falsely flag a correct answer — fixed by factoring `build_transaction_record_text()` out of `generation/prompts.py` so both call sites build identical context (see `docs/04-guardrail-attack-log.md`).
- **UC1 confidence gate added (previously ungated), UC2 stays exempt:** UC1 (general docs corpus) gets its own `UC1_CONFIDENCE_THRESHOLD`, independently tunable from UC3's — the two corpora almost certainly have different score distributions, same "tune empirically against the Phase 4 golden set" caveat PRD §14 already applies to UC3's threshold (default `0.40`, provisional). UC2 is exempt: its grounding is an exact-key Postgres lookup, not a similarity search, so a retrieval-score threshold doesn't describe confidence in the transaction facts.
- **Adversarial fixtures kept out of the seed-42 CSV:** the UC2 description-injection/PII test cases (both automated and the manual attack-log runs) use in-memory `Transaction` fixtures or temporary, reverted Postgres row edits rather than adding rows to `data/transactions/transactions.csv` — inserting into that deterministic `random.Random(42)` sequence would shift every subsequent row's draws, breaking the "regenerate identically" guarantee from the Phase 2 entry above, and would mix attack payloads into what's meant to be a clean demo dataset.

## 2026-08-14 — Phase 4 tech choices

- **LangGraph nodes stay untouched; eval harness is offline-only tooling:** `src/paymentcopilot/evals/` calls the existing `run_query()` entrypoint once per golden item rather than adding any new graph nodes or hooking into the live request path — this phase measures the system, it doesn't change its runtime behavior. `guardrails/faithfulness.py` (Phase 3's live PASS/FAIL judge) is deliberately left independent of RAGAS's `Faithfulness` metric; see `docs/01-architecture.md`'s Phase 4 section for why merging them would be a net negative (couples live-request cost/latency to eval-tooling churn).
- **`ragas.evaluate()` + `EvaluationDataset.from_list()`** (RAGAS 0.2.15, resolved from the `ragas>=0.2,<0.3` pin) over the lower-level per-metric `SingleTurnSample.single_turn_ascore()` API — the documented high-level entry point, sufficient for a 20-item `ragas_eligible` subset with no need for custom async batching. Metrics: `Faithfulness`, `ResponseRelevancy`, `LLMContextPrecisionWithReference`, `LLMContextRecall` — covers all four of §7.2's RAGAS bullets. Judge/embeddings reuse the existing Claude model and `sentence-transformers` embedder via `langchain-anthropic`/`langchain-huggingface` wrapper packages (new `requirements-eval.txt` dependency) rather than introducing a second provider.
- **`requirements-eval.txt` as a third requirements file**, not `requirements-dev.txt`: RAGAS's dependency chain (`datasets`, `langchain-core`, provider wrappers) is heavy and never touches live-request runtime, unlike `pytest`/`ruff` which every contributor needs. Installing it downgraded `packaging` (26.3→25.0) and `fsspec`/`langchain-core` to versions compatible with RAGAS 0.2.x's pins — verified via a full `pytest` run post-install that nothing in the existing Phase 1-3 suite regressed.
- **Golden dataset as JSONL** (`data/eval/golden_set.jsonl`, 43 items, 9 categories) — matches RAGAS/`datasets`' native ingestion shape and diffs cleanly per-item in git, consistent with `transactions.csv`'s existing plain-format precedent over a single structured blob.
- **Refusal-correctness = precision/recall/F1/accuracy on `escalated` vs. `expected_escalated`**, not recall alone — §7.2's "correctly refuse... **and only those**" requires penalizing over-refusal (FP), which a recall-only metric would miss entirely (a "refuse everything" strategy scores perfect recall). Reason-specificity (did the *right* guardrail fire) is a separate `StrictRefusalDiagnostics.exact_match_rate`, never blended into the primary metric, since `expected_escalated` is the contractual promise and the triggering mechanism is a secondary concern.
- **Confidence-threshold sweep re-runs `run_query` per candidate rather than simulating post-hoc** from one run's recorded retrieval scores — a post-hoc check only predicts outcomes correctly when *raising* a threshold above an item's originally-passing score; lowering it below an originally-failing score can't be simulated, since the LLM call (and faithfulness check) never actually happened the first time in that direction. See `evals/threshold_sweep.py`'s docstring.
- **Threshold sweep result — no change to `UC1_CONFIDENCE_THRESHOLD`/`UC3_CONFIDENCE_THRESHOLD` defaults.** Swept UC1 across `{0.30, 0.35, 0.40, 0.45, 0.50}` and UC3 across `{0.35, 0.40, 0.45, 0.50, 0.55}` against the golden set's happy-path + low-confidence/policy-gap subsets: **refusal-correctness was precision=1.0/recall=1.0 at every single candidate value for both thresholds.** The golden set's retrieval scores are cleanly separated between clearly-relevant and clearly-irrelevant queries within these ranges, so the existing provisional defaults (`0.40`/`0.45`, set in Phase 2) are empirically robust across the whole tested band — closing PRD §14's open question with real evidence rather than leaving it as an untested guess, even though the answer turned out to be "no change needed." A finer grid or harder near-boundary golden items would be needed to find an actual sensitivity edge, left as a backlog item if threshold tuning becomes relevant at a larger data scale.
- **Golden-set query phrasing bugs found and fixed during the first live `--skip-ragas` run** (not left as silent golden-set noise): three `uc3_happy`/`refusal_policy_gap` queries originally used "can we..." phrasing, which isn't in `classify.py`'s `POLICY_PHRASES` (only "can i" is) — reworded to "is it permitted to...", "am I allowed to...", "is [X] eligible for..." (all recognized phrases), fixing a 6-item routing misclassification (37/43 → 43/43 routing accuracy). One `uc1_happy` query lacked any `PAYMENT_DOMAIN_KEYWORDS` match and misrouted to `out_of_scope`; reworded to include "payment"/"currency"/"api". Three `adversarial_pii` query rewrites were needed because embedding PII whose *topic* related to the follow-up question (a card number + a card-error-code question; an IBAN + a currency-limits question) invited the model to comment on the PII/topic mismatch, which tripped UC1's `_NO_INFO_MARKER` self-admission substring check even though the answer was substantively grounded — final versions pair the PII with a topic entirely unrelated to the PII's domain (e.g. an IBAN + a webhook-signature question) to avoid this.
- **Known, documented system limitation surfaced by this phase (not fixed here — `guardrails/faithfulness.py` and `generation/generator.py` are explicitly out of scope for Phase 4's eval-tooling-only mandate):** the live faithfulness guardrail's LLM judge intermittently flags UC2 answers as unfaithful when the model correctly converts a transaction's smallest-currency-unit amount (e.g. `138826 INR`) into a human-readable value (`₹1,388.26`) — the judge sometimes treats this as an "unsupported conversion" rather than recognizing the grounding text's explicit `(smallest currency unit)` label as license to convert. Reproduced across every full eval run in this phase (2-4 of 43 items, always in `uc2_happy`, never deterministic — different specific items fail each run). This is the dominant cause of refusal-correctness precision landing at ~0.87 rather than 1.0, and of RAGAS's own `faithfulness` metric landing at ~0.70-0.76. A related, milder finding: UC1's `grounded = _NO_INFO_MARKER not in text` check (Phase 1) is a substring match anywhere in the answer, so a model response that hedges with "I don't have enough information..." as a preface (even while still answering substantively afterward, e.g. after flagging a security concern about PII in the query) gets marked `grounded=False` and escalates. Both are flagged here as backlog items for a future guardrail/generation-quality pass, not fixed in this eval-tooling phase.
- **First real eval run** (`docs/03-eval-results/eval-20260814-151518.{md,json}`): 43/43 routing accuracy, refusal-correctness precision=0.870/recall=1.000/f1=0.930 (limited entirely by the currency-conversion finding above — recall is perfect, meaning zero under-refusals, the safety-critical direction), RAGAS faithfulness=0.757, answer_relevancy=0.732, context_recall=0.829, context_precision=0.957.

## 2026-08-14 — Phase 5 tech choices

- **`RouterResult.query` bug fix, ahead of everything else this phase:** `run_query()` returned the raw input `query` parameter instead of the graph's internal `result["query"]`, which `_input_guardrail_node` may have overwritten with the PII-redacted text. Harmless through Phase 4 since nothing persisted `RouterResult.query` — session memory (below) is the first feature that does, and per NFR "PII never persisted unredacted" it must store the redacted query. Confirmed by grep that no other code (evals, CLI) read this field before changing it, and added a regression assertion to the existing `test_pii_in_query_is_redacted_before_reaching_generation` test.
- **Semantic cache (FR20): embed + linear-scan cosine similarity, not a Redis vector module.** At this project's scale (capped, small per-tenant lists), a Python `numpy.dot` scan over `embedder.embed_one()` output is simpler than adding RediSearch/RedisVL, and cosine similarity is a plain dot product since embeddings are already L2-normalized. The cache stores the API *response payload* dict, not `RouterResult`/`Chunk`/`Transaction`, keeping `cache/semantic_cache.py` decoupled from graph internals. Escalated/refused answers are never cached — serving a stale refusal as if it were a stable answer would be wrong once retrieval data or transaction state changes. TTL is lazy-per-entry (checked during the lookup scan) plus a backstop whole-key `EXPIRE` at 2x the TTL, since a single whole-key TTL refreshed on every write would let a heavily-hit tenant's key never actually expire individual stale entries.
- **Rate limiting (FR21): fixed-window `INCR`+`EXPIRE`, not sliding-window/token-bucket.** Simplest correct approach at this scale; the accepted tradeoff is a boundary burst admitting up to ~2x the configured limit across a window edge. Enforced as a FastAPI dependency that runs before both the semantic cache lookup and `run_query()` — even a cache lookup costs a local embed + Redis round trip, so "requests" for FR21's purposes means all incoming traffic, not just LLM-invoking calls.
- **Session memory (FR22): storage/plumbing only, history not fed into generation.** Every turn (post-guardrail redacted query, already-checked answer, route, escalated, guardrail_status, timestamp) is persisted per `session:{tenant_id}:{session_id}` with a TTL refreshed on each write. The PRD's own non-goal ("not building a general-purpose chatbot") argues against adding follow-up/pronoun-resolution logic this phase — that's deferred. A client-omitted `session_id` is still generated server-side and returned in the response (a small addition beyond minimum FR22 compliance) so a future phase has a client-visible handle to build multi-turn context on, rather than write-only plumbing nobody can reference again.
- **`tenant_id` (API) vs `merchant_id` (router/DB): translated only at the FastAPI boundary, not renamed throughout.** `prd.md` §10's indicative `/query` shape uses `tenant_id` literally; `api/app.py` translates it to `merchant_id` right where `run_query()` is called. `graph/router.py`, `structured/lookup.py`, the CLI, and their tests are unchanged — a full rename would have been a much larger diff touching already-stable Phase 1-4 code for a naming preference, not a behavior change.
- **Concurrency: `asyncio.to_thread(run_query, ...)`, not an async rewrite of Phase 1-4 internals.** `run_query()` and everything beneath it (Pinecone SDK, Anthropic SDK, psycopg) is fully synchronous; wrapping the call keeps the event loop unblocked for concurrent cache hits and `/health` checks without rewriting stable, already-tested Phase 1-4 code to be async — real scope creep the PRD doesn't require.
- **No token-level streaming (FR24's "streaming where applicable").** Phase 3's output guardrails (faithfulness check, PII-leak redaction) must run on the *complete* generated answer before it's safe to return to the client — true token streaming would either leak unvetted text before the checks run, or require buffering the full answer server-side and "fake streaming" an already-finished response with no real latency benefit. `/query` is a plain synchronous JSON response; "applicable" is read here as "not applicable, given the non-negotiable guardrail architecture."
- **Token usage tracking via a `ContextVar` accumulator (`generation/usage_tracking.py`), added to `generator.py::call_claude()`.** NFR observability requires "token usage" in structured per-request logs; this is a small, additive, non-breaking two-line addition (`record_usage(response.usage.input_tokens, response.usage.output_tokens)`) that's a no-op unless a caller opts in via `reset_usage_tracking()` — no existing call site or test (which all mock `call_claude` wholesale) is affected. `ContextVar` state doesn't propagate out of `asyncio.to_thread`, so `run_query_with_usage()` resets, calls, and reads the totals all inside the one function dispatched to the thread.
- **`POST /evals/run` gated by `ENABLE_EVALS_ENDPOINT` (default `false`), returning 404 rather than 403 when disabled** — no auth system exists in this project and none was introduced for this internal/dev-only endpoint; 404 avoids confirming the endpoint's existence to an unauthenticated prober.
- **Structured per-request JSON logging (`api/request_logging.py`) is a distinct code path from `guardrails/logging.py`'s `log_guardrail_event`.** The guardrail logger only logs when a guardrail *triggers* (`.warning()`, relying on Python's default last-resort stderr handler for visibility — deliberately minimal, security-audit granularity). The new request logger logs *every* request via a dedicated `INFO`-level handler attached directly to the `paymentcopilot.requests` logger (not `logging.basicConfig()` on the root logger, to avoid changing third-party library log verbosity) — full-lifecycle observability (route, latency, tenant, guardrail outcome, cache hit, token usage) satisfying the NFR's "structured JSON logs per request" literally. Caught during manual smoke testing: without an explicit handler, `.info()`-level logs are silently dropped by Python's logging defaults (unlike `.warning()`, which the guardrail logger relies on).
- **Docker: single-stage `Dockerfile`, model weights baked in at build time, Postgres containerized via a one-shot `seed` service.** Multi-stage's main benefit (excluding a build toolchain) is marginal here since most dependencies ship prebuilt wheels, consistent with this project's existing bias toward simplicity. Baking `sentence-transformers/all-MiniLM-L6-v2` and `en_core_web_sm` into the image at build time means the container needs no network access at runtime, avoiding cold-start latency and Hugging Face Hub rate-limit risk. `docker-compose.yml`'s `seed` service (`depends_on: postgres: condition: service_healthy`, `api` then depends on `seed: condition: service_completed_successfully`) loads the existing `data/transactions/transactions.csv` before `api` starts, so a fresh clone gets a fully self-contained local stack rather than depending on a pre-existing local Postgres install (the Phase 2 decision this supersedes for the containerized-demo path only — local non-Docker dev is unaffected). `postgres:14-alpine` was chosen to match the existing local dev Postgres major version, avoiding version-skew surprises.
- **Real bug found via the Docker verification pass (see below), fixed in `guardrails/pii.py` (Phase 3 code):** `Presidio`'s `AnalyzerEngine()` was instantiated with no explicit NLP engine config, so it silently used Presidio's actual default model, `en_core_web_lg` (~400MB) — not `en_core_web_sm`, despite the Phase 3 decisions log above stating `en_core_web_sm` was the deliberate choice. This never surfaced on the host dev machine because `en_core_web_lg` happened to already be cached there from unrelated prior work, so Presidio silently used the cached large model instead of raising or falling back to the small one. It surfaced immediately in a fresh container (nothing cached): the first PII-scanning request triggered a live 400MB download from GitHub mid-request, contradicting the Dockerfile's whole "bake weights at build time, zero network access at runtime" design goal. Fixed by explicitly constructing an `NlpEngineProvider` pinned to `en_core_web_sm` and passing it into `AnalyzerEngine(nlp_engine=...)` — matches the originally-stated Phase 3 intent, keeps behavior host/container-consistent, and doesn't change the entity list or redaction behavior (`tests/test_pii.py`, `test_router_guardrails.py` unchanged and still pass).
- **Verification: `docker-compose up --build` run end-to-end** (Docker Desktop installed partway through this phase's verification). `postgres`/`redis` reach healthy, `seed` runs and exits 0 (`Seeded 40 transactions...`), `api` starts only after `seed` completes and reports `(healthy)` on its own `/health`-based healthcheck. From the host: `GET /health` → `{"status":"ok","checks":{"redis":"ok","postgres":"ok"}}`; real UC1/UC2/UC3 queries via `POST /query` all returned correct, grounded answers; a near-duplicate repeat query hit the semantic cache (sub-40ms, no LLM call); 22 rapid requests from one tenant got 429 on requests 21-22; a PII-bearing query correctly redacted (`guardrail_status: "input_redacted:pii"`) without any runtime model download after the fix above. Confirms the Phase 5 Docker deliverable works as designed, not just as unit-tested.

## 2026-08-22 — Conversational memory in the Support Console

- **The console keeps a transcript instead of replacing one answer with the next.** Session memory (FR22) has been threaded into generation since the prior commit, but the UI still showed a single question/answer pair, so the merchant couldn't see the turns their follow-up was resolving against — a model that remembers more than the screen shows is an unreadable system. `frontend/app/page.tsx` now holds a `ChatTurn[]` and renders every turn (`components/ConversationTurn.tsx`); pending, error, and answered states all live on the turn rather than on the page, so a failed request no longer wipes the conversation before it.
- **"New conversation" drops the `session_id`, not just the transcript.** The old "New question" control cleared the visible answer but kept the session id, leaving the backend answering against turns the merchant could no longer see. Clearing both is the only state where what's on screen and what's in the prompt agree; the old Redis key is left to expire on its own TTL rather than adding a delete endpoint.
- **Context-dependent queries bypass the semantic cache in both directions (`cache/semantic_cache.py::is_context_dependent`).** FR20's cache is keyed on query text per *tenant*, while FR22's memory is per *session* — so with multi-turn follow-ups now realistic, "why did that fail?" asked in one conversation could be served from, or poison, an unrelated one. Queries containing anaphora (`it`, `that`, `the second one`, …) therefore neither read from nor write to the cache. The regex is deliberately over-inclusive: a false positive costs one cache hit and falls through to the full pipeline, while a false negative answers a merchant with someone else's conversation. Not scoped to "only when history exists", because the poisoning risk is at *write* time, when the writing session's own history says nothing about who reads the entry later.
- **The memory window is surfaced, not hidden.** The composer footer states how many of the backend's `MAX_HISTORY_TURNS` (5) turns go into the next answer, and each follow-up turn is labelled with the count it was answered against — consistent with the rest of this frontend, where the system's actual behavior (route, grounding, guardrails, trace) is shown rather than implied.
