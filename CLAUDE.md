## What this is

Payment Copilot is a multi-tenant, production-styled RAG gateway that answers merchant support queries for a payment API platform (Razorpay/Stripe-style). It routes each query to one of three use cases — docs Q&A (UC1), structured transaction lookup (UC2), or policy-grounded refusal (UC3) — through a deterministic LangGraph router, with input/output guardrails, an offline eval harness, and a FastAPI gateway. See `prd.md` for full product requirements and `docs/01-architecture.md` for the phase-by-phase design (each phase section documents its own topology/diagram). All docs/transaction/policy data is synthetic; no real merchant or PII data.

## Commands

### Setup
```
python3.11 -m venv .venv && source .venv/bin/activate
pip install -e .
python -m spacy download en_core_web_sm   # required by Presidio PII guardrails
cp .env.example .env                       # fill in ANTHROPIC_API_KEY, PINECONE_API_KEY
python scripts/verify_setup.py
```
Eval-only deps (RAGAS, not needed at runtime): `pip install -r requirements-eval.txt`
Dev deps (pytest, ruff, fakeredis): `pip install -r requirements-dev.txt`

Runtime services: Postgres (`DATABASE_URL`, default `postgresql://localhost/paymentcopilot`) and Redis (`REDIS_URL`, default `redis://localhost:6379/0`) must be reachable locally, or use `docker-compose up --build` which containerizes both plus a one-shot seed step.

### Lint & test
```
ruff check .
pytest -q
pytest tests/test_router_guardrails.py -q          # single file
pytest tests/test_router_guardrails.py::test_name -q   # single test
```
CI (`.github/workflows/ci.yml`) runs exactly `ruff check .` then `pytest -q` on every PR/push to main, using dummy `ANTHROPIC_API_KEY`/`PINECONE_API_KEY` — every test mocks the Anthropic/Pinecone/Postgres call sites, no live services needed. The autouse `_stub_ml_injection_scanner` fixture in `tests/conftest.py` stubs the ML injection fallback so the suite never loads the real DeBERTa classifier; tests exercising that path patch `paymentcopilot.graph.router.scan_injection_ml` directly.

## Architecture

### Request path (`src/paymentcopilot/graph/router.py`)
Every query goes through a compiled LangGraph state machine, not a single LLM call — each step is a distinct, loggable node (PRD FR2):

`classify → input_guardrail → {uc1_docs | uc2_transaction | uc3_policy | out_of_scope | blocked} → output_guardrail → END`

- **classify** (`graph/classify.py`) — regex/heuristic router: `TXN_ID_RE` match → UC2, else keyword/embedding-based UC1 vs UC3 vs out-of-scope.
- **input_guardrail** — runs injection scan (regex first via `guardrails/injection.py`, then ML fallback `guardrails/injection_ml.py` only if regex passes, since the ML scanner is a model inference and more expensive) and PII scan/redact (`guardrails/pii.py`, Presidio). Injection match → routes to `blocked`; PII found → query is redacted in place and the graph continues.
- **uc1_docs** — retrieves top-k doc chunks (`retrieval/retriever.py`, Pinecone) and generates a grounded answer (`generation/generator.py`); ungrounded → `escalated=True`.
- **uc2_transaction** — looks up the transaction by ID scoped to `merchant_id` (tenant isolation — cross-tenant lookups always miss), separately guardrails the transaction's free-text `description` field (injection + PII, same as query input) before it reaches the LLM, and falls back to a templated (non-LLM) answer if the description is flagged as injection.
- **uc3_policy** — same shape as UC1 but retrieves from the policy corpus and is refusal-oriented (grounded refusal when policy doesn't support the ask).
- **output_guardrail** — skipped if already escalated; else runs LLM-as-judge faithfulness check (`guardrails/faithfulness.py`) against the grounding text (retrieved chunks + transaction record), then PII redaction on the answer itself.
- **guardrail_status** accumulates as a comma-joined string of tags (`_append_status`) so a single response can reflect multiple guardrail events (e.g. input PII redaction *and* output faithfulness block).

Confidence thresholds (`UC1_CONFIDENCE_THRESHOLD`, `UC3_CONFIDENCE_THRESHOLD` in `config.py`) gate whether UC1/UC3 answers are treated as grounded vs escalated; tune via `evals sweep-thresholds`, not by hand-editing defaults.

### Layers
- `graph/` — LangGraph router + query classifier (orchestration only, no business logic).
- `retrieval/`, `embeddings/`, `ingestion/` — Pinecone-backed vector search for UC1/UC3; `ingestion/chunker.py` + `loader.py` build the corpora, `ingestion/ingest.py` drives embed+upsert.
- `structured/` — UC2 transaction lookup: `db.py` (Postgres), `lookup.py` (tenant-scoped query), `error_codes.py` (static error-code explanations).
- `guardrails/` — injection (regex + ML), PII (Presidio), faithfulness (LLM-judge), confidence gating; `logging.py` emits structured guardrail events, `messages.py` centralizes user-facing refusal/block copy.
- `generation/` — prompt construction (`prompts.py`) and Claude calls (`generator.py`); `usage_tracking.py` for token/cost accounting.
- `cache/` — Redis-backed semantic cache (near-duplicate query short-circuit), per-tenant rate limiter, session memory, and per-request trace store (`trace_store.py`, powers `GET /trace/{request_id}`).
- `api/` — FastAPI app (`app.py`), request schemas, `attack_lab.py` (curated adversarial test cases for the frontend Attack Lab), `request_logging.py`, `dependencies.py`.
- `evals/` — offline harness: golden-set loader, refusal-correctness + routing-accuracy custom metrics, RAGAS integration, threshold sweep, Markdown/JSON report writer. Not part of CI (separate `requirements-eval.txt`, makes real LLM-judge calls).
- `cli.py` — the only user-facing entrypoint for `ingest`/`ask`/`evals run`/`evals sweep-thresholds`; keep new operator-facing commands here rather than one-off scripts, unless they're setup/seed scripts (which live in `scripts/`).

### Cross-cutting notes
- Everything reads config through the single frozen `Settings` dataclass in `config.py` (`load_settings()`, instantiated once as module-level `settings`) — don't read `os.environ` directly elsewhere.
- Tenant isolation (`merchant_id`) is enforced at the UC2 lookup layer (`structured/lookup.py`) — any new structured-data feature must scope queries the same way.
- Guardrails apply symmetrically to both the user query and any untrusted text pulled from data (e.g. a transaction's `description` field) before it's shown to the LLM — see `_uc2_node`'s description-injection/PII handling for the pattern to follow when adding new untrusted-text sources.
- `docs/04-guardrail-attack-log.md` tracks known adversarial prompts and their outcomes — check it before assuming a new injection pattern is undocumented, and add entries for new ones found.
